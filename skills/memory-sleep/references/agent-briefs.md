# Задания агентам

Шаблоны для волн сна. Подставь: `{MEM}` — папка памяти, `{RUN}` — папка прогона, `{TODAY}` — сегодняшняя дата, `{LAST}` — дата прошлого сна и путь к папке его прогона (или «прошлого сна не было»), `{STYLE}` — одна строка с языком и запретами владельца для текстов.

Каждому агенту в начале сообщай три вещи: что это фаза консолидации файловой памяти кодового агента; что ему разрешено менять (почти всегда ничего, кроме своего файла результата); в каком виде вернуть ответ тебе (коротко: счетчики и главное, подробности в файле). Агент ничего не знает о прогоне, кроме твоего текста.

Для чтения, сверки и экзаменов хватает модели попроще, если харнесс позволяет выбрать; сжатие индекса, проверку потерь и кошмар оставляй основной модели.

Содержание:
1. Отбор по расшифровкам
2. Сверка с диском
3. Аудит N3
4. Экзаменатор
5. Экзамен (до и после сна)
6. REM: узоры между проектами
7. REM: дальние пары
8. Кошмар
9. Сжатие индекса
10. Проверка потерь
11. Утренняя шпаргалка

---

## 1. Отбор по расшифровкам

```
Ты фаза отбора в консолидации памяти кодового агента: ищешь то, что владелец сказал
за последние дни, а в память не попало. Только чтение; пишешь один новый файл.

Реплики владельца уже собраны: {RUN}/user-turns.md (по сессиям, с датами; в заголовке сессии указан источник: claude или codex). Читай частями.
В файле может остаться шум: запросы, которые отправил инструмент, а не владелец, и повторы одной
реплики. Пропускай их. Одна и та же реплика в двух файлах одной сессии — это одна реплика.

Ищи реплики трех видов:
1. Поправки и недовольство: владелец останавливает, переделывает, повторяет уже сказанное.
2. Стоячие предпочтения и правила: «всегда», «никогда», «запомни», «впредь», «по умолчанию».
3. Факты о мире владельца, которые пришлось бы повторять: люди и их роли, адреса ресурсов,
   где лежит ключ (только место, не значение), договоренности с датами.

Сверь с памятью: {MEM}/MEMORY.md и файлы по его ссылкам, плюс файлы инструкций владельца
(CLAUDE.md, AGENTS.md), если они есть. Для каждого кандидата реши операцию:
- ADD: в памяти этого нет, правило прочное и пригодится в будущих сессиях; предложи имя нового
  файла памяти в формате, принятом в {MEM}, и его полный текст;
- UPDATE: есть файл, который надо дополнить (назови какой);
- NOOP: уже покрыто, либо разовое указание по одной задаче.
Будь строг: сказанное один раз по ходу задачи — NOOP. Сильный кандидат — то, что владелец
повторил в двух разных сессиях.

Если в репликах встретился секрет открытым текстом, не цитируй его: укажи только сессию и дату.

Запиши {RUN}/transcripts.md: таблица «операция | что именно | цитата (до 150 знаков) |
сессия и дата | файл памяти». Для ADD и UPDATE приложи готовый текст. {STYLE}
Мне верни счетчики ADD / UPDATE / NOOP и по строке на каждый ADD и UPDATE.
```

## 2. Сверка с диском

```
Проверка памяти на соответствие реальности, только чтение. Ничего не изменяй, не удаляй,
не коммить, не пушь, не запускай сборки и деплои.

Файл {RUN}/realityN.txt содержит строки индекса памяти со ссылками на файлы в {MEM}.
Сегодня {TODAY}.

Для каждой строки проверь утверждения, которые проверяются за 1-3 команды:
- упомянутые пути существуют;
- если это git-репозиторий: дата и хеш последнего коммита, незакоммиченные правки,
  незапушенные коммиты (git status -sb, git log -1 --format='%h %ad' --date=short).
  Состояние удаленного репозитория бери из локального кэша git и помечай «по кэшу»;
- [только если сеть разрешена] публичные адреса: curl -s -o /dev/null -w '%{http_code}' -m 8,
  только код ответа;
- прошедшие даты и статусы «ждет X»: открой файл по ссылке, посмотри последние записи
  и скажи, отражает ли строка индекса последнюю из них;
- если в каталоге проекта есть правки новее последней записи памяти больше чем на 7 дней,
  отметь. Возраст записи бери по датам внутри файла, не по времени изменения файла.

Как ставить вердикт в спорных случаях:
- в строке нет ни пути, ни другой опоры на диске, либо проверка требует сети — «не проверить»,
  в колонке расхождений напиши, чего не хватило;
- подтвердилась только часть утверждений — вердикт по худшему из проверенных, непроверенное
  перечисли;
- новые коммиты есть, но содержимого проекта они не меняют (служебные файлы инструментов) —
  «свежо» с примечанием.
Одна строка таблицы на запись; ошибся — исправь строку, а не дописывай поправку ниже.

Не читай файлы с секретами (.env, *.key). На всю пачку у тебя столько времени, сколько назвал
оркестратор: не успеваешь — проверь меньше утверждений на строку, но пройди все строки.

Запиши {RUN}/realityN.result.md: таблица «запись | вердикт (свежо / устарело / неверно /
не проверить) | что расходится | предлагаемая новая строка (только для «устарело» и «неверно»,
в формате исходной, до 220 знаков)». В конце счетчики. {STYLE}
Мне верни счетчики и расхождения по одной строке.
```

## 3. Аудит N3

```
Ты фаза глубокого сна (N3) в консолидации файловой памяти кодового агента. Только чтение
памяти, результат в один новый файл.

Память: {MEM} (индекс MEMORY.md и файлы по его ссылкам). Прошлый сон: {LAST}; если он был,
в его папке лежат заметки: phases.log, отчет и файлы фаз (n3.md, rem.md, nightmare.md — какие
есть). Сегодня {TODAY}.

Сделай четыре вещи:
1. Отбор. Найди записи с датами после прошлого сна (или за последние 14 дней). Смотри на даты
   внутри записей: время изменения файла обманывает после массовых правок. Для каждой
   затронутой темы скажи, отражена ли самая свежая запись в строке индекса. Дай список строк,
   где индекс отстал, с предлагаемой заменой (до 220 знаков, в формате индекса).
2. Перенос уроков. Найди сбои и ошибки, которые повторяются в двух и более местах памяти.
   Проверь, стал ли каждый общим уроком (в базе знаний или отдельном файле). Для отсутствующих
   напиши готовый текст урока в формате, принятом в этой памяти (посмотри 2-3 существующих
   записи), опираясь на конкретные записи. Деталей не выдумывай: если в записях нет решения,
   оставь раздел решения пустым с пометкой «в записях нет».
3. Долг прошлого сна. Рекомендации прошлого сна — это все, что его отчет и файлы фаз предлагали
   сделать и оставили владельцу: правки, уроки, угрозы, кандидаты на ослабление. По каждой
   отметь: сделано / не сделано / неизвестно.
4. Строки без ссылок. Если оркестратор дал файл {RUN}/reality-unlinked.txt, по каждой его строке
   скажи: актуальна, устарела (чем подтверждается) или не проверить.
5. Кандидаты на ослабление. Записи, которые давно не обновлялись и ни на что не влияют,
   дубли, строки индекса, повторяющие друг друга. Только список с обоснованием; ничего не удалять.

Запиши {RUN}/n3.md. {STYLE}
Мне верни счетчики по разделам и готовые тексты уроков.
```

## 4. Экзаменатор

```
Ты экзаменатор. Составь экзамен, которым измеряется извлекаемость фактов из файловой памяти
кодового агента. Только чтение памяти: {MEM}.

Составь 12-16 вопросов такого рода, какие владелец задает в начале рабочей сессии: где лежит X,
что блокирует Y, какой следующий шаг по Z, какое правило действует про W, какой был урок про V.
Главное требование: половина ответов видна уже в MEMORY.md, половина только в файлах по ссылкам.
Темы бери разные: проекты и дела (в том числе с записями за последние две недели), правила
владельца, уроки, справочные сведения, один-два сквозных вопроса (ответ требует двух файлов).
Ответ на каждый короткий и однозначный: путь, адрес, число, имя, одно предложение.
Каждый эталонный ответ сверь с файлом-источником, а не только со строкой индекса.

Запиши два файла:
- {RUN}/exam-questions.md: только нумерованные вопросы, без ответов и подсказок;
- {RUN}/exam-key.md: номер, эталонный ответ, файл-источник, виден ли ответ в индексе (да/нет).
{STYLE}
Мне верни одну строку: сколько вопросов и сколько из них с ответом в индексе.
```

## 5. Экзамен (до и после сна)

До сна и после сна индекс один и тот же путь, `{MEM}/MEMORY.md`: экзамен после сна проводится уже после подмены индекса. Файлы ответа — `exam-answers-before.md` и `exam-answers-after.md`. Ответы с ключом сверяешь ты сам.

```
Ты сдаешь экзамен на извлекаемость фактов из файловой памяти. Только чтение.

Вопросы: {RUN}/exam-questions.md. Больше ничего из {RUN} читать нельзя, особенно файлы
с key и answers в имени: это обнуляет экзамен.

Правила. Сначала прочитай индекс <путь к индексу> один раз (если он уже есть в твоем контексте,
отдельно не открывай). На каждый вопрос сначала попробуй
ответить только по индексу. Если индекса мало, можно открыть не больше двух файлов из {MEM}
на вопрос, выбирая их по ссылкам индекса, по одному под конкретный вопрос. Поиск по каталогу
памяти и по диску запрещен. Не нашел — пиши «не найдено», не гадай.

Запиши <файл ответа>: по строке на вопрос «N | ответ | сколько файлов открыл (0, 1, 2) | какие»
(если файлов не открывал, в последнем поле прочерк).
{STYLE}
Мне верни одну строку: сколько отвечено по одному индексу, сколько с файлами, сколько не найдено.
```

## 6. REM: узоры между проектами

```
Ты фаза REM в консолидации файловой памяти кодового агента: сопоставляешь записи из разных
мест памяти, чтобы увидеть то, чего не видно внутри одного проекта. Только чтение: {MEM}.

Найди, с опорой на конкретные записи (файл и номер или дата записи):
1. Повторяющиеся сбои: один класс ошибки в двух и более проектах. Для каждого: название,
   где встречался, есть ли уже общий урок.
2. Переносимые уроки: решение, найденное в одном проекте, которое помогает делу,
   застрявшему в другом.
3. Правила владельца, которые противоречат друг другу, дублируются или устарели с учетом
   более поздних записей.
4. Узкие места: чего или кого одновременно ждут несколько дел.

Кратко и конкретно. Не выдумывай: если опора слабая, так и напиши.
Запиши {RUN}/rem.md, до ~900 слов. {STYLE}
Мне верни по одной строке на находку.
```

## 7. REM: дальние пары

```
Ты ищешь переносимые механизмы между несвязанными записями памяти владельца.
Только чтение памяти и диска.

Пары выбраны жребием, менять их нельзя: {RUN}/pairs.txt.

Для каждой пары три шага.
1. Прочитай оба файла (большой файл: оглавление и последние 10 записей). Найди неочевидный
   переносимый механизм: прием, структура данных, проверка, формат или провал из одного,
   который решает что-то реальное в другом или порождает третью вещь. Банальности
   («общий дашборд», «пост про оба») запрещены. Если прямого переноса нет, ищи структурную
   аналогию: что в А играет ту же роль, что X в Б. Сформулируй 2-3 кандидата.
2. Проверка реальности. Для каждого кандидата проверь опоры по диску: существует ли путь,
   файл, скрипт, на который идея опирается (ls, head, git log -1). Кандидата без подтвержденной
   опоры отбрось и запиши почему.
3. Оставь одну идею на пару и уточни ее по найденным фактам.

Запиши {RUN}/ideas.json: массив объектов с полями title (до 60 знаков), entries (две записи
пары), what (2-3 предложения), first_step (одно действие на 15 минут), dropped (отброшенные
кандидаты с причиной). {STYLE}
Мне верни три заголовка и число отброшенных кандидатов.
```

## 8. Кошмар

```
Ты фаза «кошмар» в консолидации памяти кодового агента: кошмары репетируют опасности заранее.
По файловой памяти владельца найди то, что с наибольшей вероятностью сломается, пропадет
или тихо умрет в ближайшие 2-4 недели, если ничего не делать. Только чтение; на диске можно
проверять факты командами чтения.

Память: {MEM}. Сегодня {TODAY}. Результаты сегодняшней сверки с диском: {RUN}/reality*.result.md
(прочитай все).

Четыре класса угроз:
1. Необратимая потеря: работа существует только локально (не закоммичено, не запушено,
   нет удаленного репозитория, нет копии базы), файлы во временных каталогах, единственные копии.
2. Тихая смерть: фоновые процессы, расписания, боты, платные площадки, истекающие токены,
   домены, сертификаты, пробные периоды. Что из этого сейчас никто не наблюдает.
3. Протухшие обязательства перед людьми: обещанное с датами, которые прошли или близко.
4. Секреты и личные данные: неротированные ключи после инцидентов, личные данные
   в публичных местах.

Опорный факт каждой угрозы проверь одной-двумя командами чтения, если это возможно
(git status -sb, git remote -v, ls, дата файла). Системные службы не трогай, .env и *.key
не читай. У каждой угрозы должна быть ссылка на запись памяти или результат команды.

Запиши {RUN}/nightmare.md: до 12 угроз по убыванию «вероятность x необратимость»; для каждой:
что случится, опора, одно действие на 15 минут, которое ее снимает. {STYLE}
Мне верни верхние пять по одной строке.
```

## 9. Сжатие индекса

```
Ты фаза синаптического даунскейлинга в консолидации файловой памяти кодового агента:
индекс разросся, его надо ужать без потери фактов.

Твоя пачка строк индекса: {RUN}/shrinkN.txt (заголовок раздела, под ним строка). Файлы
по ссылкам лежат в {MEM}. Сам MEMORY.md не трогай.

Правила.
1. Каждую строку сохранить, ссылку и ее цель не менять. Формат: `- [Название](файл.md) — суть`.
2. Строка проекта отвечает на три вопроса: что это, в каком состоянии, где лежит (путь
   или адрес). Цель до 200 знаков. Хотя бы одно из двух, путь или адрес, остается в строке.
3. Хеши, перечни файлов, числа, промежуточные даты убирай из строки, только если они есть
   в файле по ссылке. Если факта там нет, сначала допиши его дословно в конец этого файла
   в раздел «## Сводка из индекса памяти (перенесено {TODAY})», потом убирай из строки.
   Дописывать в конец можно; удалять и переписывать в файлах ничего нельзя.
4. Строки правил владельца: формулировку можно сжать, смысл и слова, по которым правило
   ищут, сохранить. Имена, даты и суммы не выбрасывать.
5. Действия («сделать», «спросить», «ждет») не терять: это напоминания, ради них индекс читают.
6. Факты не менять, новых не добавлять, смысл не «улучшать».

Запиши {RUN}/shrinkN.result.md: под тем же заголовком раздела новая строка для каждой исходной,
в исходном порядке. Ниже журнал: какие факты куда дописаны. {STYLE}
Мне верни: сколько строк сжато, сколько байт было и стало, в сколько файлов дописано.
```

## 10. Проверка потерь

```
Ты проверяющий после сжатия индекса файловой памяти. Только чтение; пишешь один файл отчета.

До сжатия: {MEM}/MEMORY.md. После (кандидат): {RUN}/MEMORY.new.md. Механическая проверка уже
сделана: {RUN}/check.json (структура, ссылки, список идентификаторов, пропавших и из индекса,
и из файла-цели). Журналы сжатия: {RUN}/shrink*.result.md.

Проверь то, что скрипт не видит:
1. Каждую запись из lost_facts в check.json: это настоящая потеря или факт записан в файле
   другими словами.
2. Искажения: строки, где сжатие изменило смысл (другой статус, перепутанная дата, склеенные
   разные факты, утраченное отрицание).
3. Навигация: строки, в которых не осталось ни пути, ни адреса, хотя в старой были.
4. Действия: пункты «сделать / удалить / спросить / решить / ждет», которые были в старом
   индексе и исчезли из нового, даже если остались в файле.

Запиши {RUN}/verify.md: по каждому пункту список находок со старой и новой строкой
и готовой исправленной строкой. {STYLE}
Мне верни счетчики: потери, искажения, строки без навигации, пропавшие действия.
```

## 11. Утренняя шпаргалка

